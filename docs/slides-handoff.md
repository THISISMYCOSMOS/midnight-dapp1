## 이 작업

발표 **파트 ①·②의 슬라이드**를 만든다. ③(코드+데모)은 컴파일 이후 별도.

**발표 3파트 구조 (`AGENTS.md` §2.3):**
- ① 아이디어 설명 — 세 성질의 충돌 (~2분)
- ② 아이디어를 미드나잇으로 어떻게 풀었나 (~4분)
- ③ DApp 코드 + 적용된 미드나잇 기술 특징. 데모 영상은 ③에서 재생 (~4분)

**①·②를 먼저 완성한다. 둘 다 컴파일과 독립이다. ③ 코드·데모가 죽어도 ①·②로 발표가 성립해야 한다.**

## 청중과 톤 (확정)

- **청중: 블록체인 입문.** ZK·witness·Merkle을 비유로 풀어 설명한다. 원시적 개념에 시간을 쓰고 코드 디테일은 최소
- **파트 ① 도입: 세 성질만 추상적으로.** 구체 시나리오(갑을 후기 등)로 열지 않는다
- 슬라이드는 **발표자의 말을 받쳐주는 시각 장치**다. 문장을 채우지 않는다 (`AGENTS.md` §2.6)

## 디자인 시스템 (`AGENTS.md` §2.6, `docs/mockup.html`과 동일)

- 무채색 5개(`#FFFFFF #1A1A1A #6B6B6B #A0A0A0 #E5E5E5`) + 유채색 1개 `#2F6F5E`(강조 최소, 증명/핵심 한 곳)
- 타이포 3단계, 간격 4단계. 이모지·그라데이션·그림자·둥근 카드 금지
- 위계는 크기 폭주가 아니라 웨이트와 여백으로. 제품이 자기를 해설하는 문장 금지

## 정밀함 — 이게 발표의 핵심이다 (`AGENTS.md` §2.5)

**위조(authenticity)와 익명(anonymity)을 절대 섞지 않는다.** 둘은 다른 위협이다:
- 위조 = "자격 없는 놈이 통과한다" (보안)
- 특정/연결 = "쓴 사람이 누구인지 드러난다" (익명)

같은 "온체인 공개"라도 `ownPublicKey`의 정답 공개는 **위조**를 쉽게 만들고, Set 조회의 값 노출은 **특정**을 만든다. 슬라이드·구두에서 이 구분을 유지한다.
- **"특정"이라는 단어는 익명 문맥에만 쓴다.** 값을 알아내 위조하는 건 "admin 값이 공개돼 베낄 수 있다"로 말한다
- Merkle은 "내가 나임을 증명"이 아니다 → "명단의 어떤 비밀을 소유했음을, 그게 어느 것인지는 안 밝히고 증명"

## 확정된 내용 스파인 (사용자가 이미 학습·확정함)

**파트 ① — 세 성질의 충돌**
- 후기 게시판, 세 성질: 누가 썼는지 아무도 모름(운영자 포함) / 아무나 못 씀(자격자만) / 상품당 1회
- 왜 모순처럼 보이나: 자격 확인 = 명단에서 너를 찾아 대조 = 특정. 그래서 익명과 안 섞임
- 보통 익명은 반쪽짜리 — 사용자 간에만 익명이고 운영자(대조표 쥔 자)에겐 노출. 로그인(운영자가 앎) or 완전개방(도배) 둘 중 하나
- 한 줄 메시지: "누가 썼는지는 아무도 모르지만, 아무나 쓸 수는 없다"

**파트 ② — 미드나잇으로 어떻게 (핵심: 세 성질이 전부 두 파생 도장에서 나온다)**
- 열쇠: 신원 대신 **비밀키로 해시 도장 두 개**를 찍는다
  - `reviewerKey = H("review:pk:v1", sk)` (자격용)
  - `nullifier = H("review:null:v1", itemId, sk)` (중복용)
  - 해시 성질 → 일방향(도장 봐도 sk 역산 불가=익명) / 충돌저항(남이 위조 불가=나만 만듦) / 도메인분리(두 도장 서로 안 엮임=비연결)
- **자격 = Merkle 멤버십 (②의 정점)**: 도장(잎)들을 두 개씩 짝지어 해시 → 루트 하나. 온체인엔 루트만. 증명 시 내 잎+경로를 witness로 넣어 회로가 루트 재계산→대조. **밖으로 나가는 건 "루트 일치"뿐, 내 잎이 뭔지·몇 번째인지는 안 나감.** Set이면 조회할 때 값을 넘겨 노출 → 그래서 Merkle
- **중복 = nullifier**: 공개하되 신원·다른 도장과 비연결. 자격·중복은 제출 전 브라우저에서 즉시 판정(증명 없이) → 실패는 사후 에러가 아니라 사전 상태 (`docs/ux-flow.md` §2.3)
- **익명을 지키는 건 두 개의 끊긴 링크**: 해시(일방향)가 "도장↔사람"을 끊고, witness 경로가 "나↔어느 잎"을 끊는다. **자격 명단(도장 목록)은 공개다 — 숨기지 않는다** (익명성 크기를 보여주려고, ux-flow §2.2)
- **반례 = `ownPublicKey`의 "두 겹의 실패"**: ②엔 **한 문장 티저만** — "순진한 방법(관리자 키 직접 비교)은 뚫린다. 미드나잇 공식 예제조차 그렇게 틀렸었다." 상세 해부는 ③ 코드에서 회수 (강화판 배치, 사용자 확정)
  - 참고(③용): 겹1 = 그 값은 증명자가 채우는 값이라 서명자와 미결합 → 소유 없이 주장만 / 겹2 = 비교 대상 admin이 공개 → 정답 베끼기 쉬움. 둘 다 있어야 우회 성립 (§2.5)
  - 실행 가능한 비교 화면: 웹 UI의 `/compare`. 블라인드 리뷰 게시판에서 같은 리뷰를 비교용 unsafe 계약과 최종 Merkle 계약에 함께 제출해 `잘못 통과`와 `거부`를 나란히 보여준다. 녹화 원본은 `docs/blind-review-comparison-demo.webm`
- 미드나잇 기술 특징(witness=오프체인 비밀 / ZK circuit / MerkleTree ledger / Kachina 공개·비밀 경계)은 각 슬라이드 하단에 태그로만 얹어 무겁지 않게

## 제안 스토리보드 (새 채팅이 다듬어라)

- ① S1 제목/한 줄 메시지 · S2 세 성질 · S3 왜 어렵나(반쪽짜리 익명)
- ② S4 도장 두 개(해시 성질) · S5 Merkle 멤버십(정점, 잎→루트 그림 + Set 반례) · S6 nullifier·사전판정 · S7 ownPublicKey 티저 한 줄
- 타이머 실측으로 ① ~2분, ② ~4분 맞춘다 (`AGENTS.md` §5 슬라이드 체크리스트)

## 작업 방식

1. **슬라이드별 스토리보드(장당 그림/한 줄)를 마크다운으로 먼저** 짜서 사용자와 확정한다. 바로 완성본을 뽑지 않는다
2. ①을 먼저 하고 사용자 검토 후 ②로 넘어간다
3. 확정되면 최종 형식으로 렌더
