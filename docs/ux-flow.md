# 사용자 흐름 · 기획

작성 2026-07-22 · 목업보다 먼저. 화면은 이 문서에서 도출된다.

---

## 1. 이 앱이 하는 일

상품에 대한 후기 게시판이다. 단:

- **누가 썼는지는 아무도 모른다** — 운영자 포함
- **아무나 쓸 수는 없다** — 자격자 명단에 있어야 한다
- **한 상품에 한 번만 쓸 수 있다**

세 문장이 서로 충돌하는 게 이 앱의 전부다. 셋을 동시에 만족시키는 방법이 발표의 내용이다.

## 2. 암호학이 UX를 결정하는 지점

디자인 취향이 아니라 프로토콜에서 나오는 제약이다. 여기서 흐름이 결정된다.

### 2.1 값이 어디에 있는가

| 값 | 어디에 | 누가 볼 수 있나 |
|---|---|---|
| `secret key` | 사용자 브라우저 로컬 | 본인만 |
| `reviewerKey` = H("review:pk:v1", sk) | 로컬에서 계산 | 본인만 |
| `eligible` Merkle 트리 | 온체인 | 전원 |
| `nullifier` = H("review:null:v1", itemId, sk) | 온체인 | 전원. 신원과 연결 불가 |

### 2.2 등록과 작성은 다른 시점이다

파생키를 공개해도 되는지가 시점에 따라 갈린다.

운영자가 자격을 부여할 때는 공개돼도 된다. 자격자 명단이 드러날 뿐, 누가 무엇을 썼는지는 나오지 않는다. 명단 크기가 보이는 편이 오히려 낫다. 1024명 중 하나라는 숫자가 곧 익명성의 크기이고, 그 숫자를 감추면 익명성이 얼마나 되는지 아무도 모른다.

리뷰를 쓸 때는 공개하면 안 된다. 이 시점에 파생키가 나가면 명단과 대조돼 작성자가 특정된다. 여기서는 Merkle 경로로 "명단 안에 있다"만 증명하고 어느 잎인지는 밝히지 않는다.

Merkle 트리를 쓰는 이유가 이것이다. 단순 명단이면 조회할 때 값을 넘겨야 하고, 넘기는 순간 끝난다.

Compact 0.31.1 생성 TypeScript API에서 `eligible.findPathForLeaf(reviewerKey)`를 직접 호출할 수 있음을 확인했다.
따라서 아래 자격 사전 판정은 ledger 상태만으로 수행한다. 이 조회는 공식 문서상 O(n)이므로 현재 깊이 10 데모 범위에만 사용한다.

### 2.3 실패는 대기 앞에 온다

자격 여부와 중복 여부는 제출 전에 브라우저에서 알 수 있다. 명단과 nullifier 집합이 둘 다 공개고 `sk`는 로컬에 있으니, 파생키를 계산해 명단에서 찾고 nullifier를 계산해 집합에서 찾으면 증명을 돌리기 전에 결과를 안다.

20초짜리 증명을 다 돌린 뒤에 "이미 리뷰하셨습니다"를 띄우면 설계가 잘못된 것이다. 버튼이 처음부터 눌리지 않고, 왜 안 눌리는지가 그 자리에 적혀 있어야 한다.

"사용자 흐름을 배려했다"는 인상은 여기서 나온다. 장식이 아니라 프로토콜에서 도출된다.

### 2.4 대기는 숨기지 않는다

증명 생성에 수 초에서 수십 초가 걸린다. 이 앱에서 유일하게 긴 대기이고, 따라서 움직임을 허용하는 유일한 지점이다. 가짜 진행바를 돌리지 않는다. 실제 단계를 보여준다.

### 2.5 화면에 띄우지 않는 것

`reviewerKey` 전체 값은 화면에 두지 않는다. 화면에 있으면 스크린샷·어깨너머·발표 영상으로 샌다.

"내가 쓴 리뷰" 표시도 목록에는 넣지 않는다. 로컬에서 nullifier로 매칭할 수는 있지만, 목록에 표시하는 순간 옆에서 보는 사람에게 작성자가 노출된다. 제출 직후 확인은 별도로 다룬다.

## 3. 등장 인물

| 역할 | 하는 일 | 이번 범위 |
|---|---|---|
| **독자** | 리뷰를 읽는다. 지갑 불필요 | 화면 있음 |
| **작성자** | 자격이 있으면 리뷰를 쓴다 | 화면 있음 |
| **운영자** | 자격자를 `eligible` 트리에 등록한다 | **화면 없음. CLI로 처리** |

운영자에게 화면을 주지 않는 것은 예산 문제만은 아니다. 실제 서비스라면 구매 확인 시스템이 자동으로 등록하므로 사람이 누르는 화면 자체가 없다. 데모에서도 CLI로 보여주는 편이 실제에 가깝다.

다만 자격을 어떻게 얻는지는 데모에서 반드시 보여준다. 그 장면이 없으면 "결국 운영자가 다 아는 것 아니냐"는 의심이 남는다.

## 4. 주 흐름

```
[진입]
  리뷰 목록이 바로 보인다. 지갑 연결 요구 없음
        │
        ▼
[리뷰 쓰기] 누름
        │
        ├─ 지갑 미연결 → 연결 요청
        ▼
[로컬 판정]  ← 온체인 호출 없음. 즉시
  sk에서 reviewerKey · nullifier 계산
        │
        ├─ 자격 없음   → 폼 비활성 + 이유
        ├─ 이미 작성함 → 폼 비활성 + 이유
        └─ 통과
        ▼
[작성 폼]
        │
        ▼
[증명 생성]  ← 유일한 긴 대기
  1. 자격 경로 확인
  2. 증명 생성        ← 대부분의 시간
  3. 트랜잭션 전송
        │
        ├─ 실패 → 원인별 문구 + 재시도 (본문 보존)
        ▼
[제출됨]
  이 화면에서만 내 리뷰를 확인할 수 있다
        │
        ▼
[목록]
  새 리뷰가 섞여 있다. 어느 것이 내 것인지 표시되지 않는다
```

지갑을 늦게 요구하는 것과 판정을 앞으로 당기는 것, 두 가지가 이 흐름의 뼈대다. 진입하자마자 지갑 연결부터 시키는 것은 Web3 앱의 기본값이자 가장 흔한 이탈 지점인데, 읽기에는 지갑이 필요 없으므로 요구할 이유가 없다.

### 제출 확인을 어떻게 할 것인가

익명이면 자기가 쓴 글도 못 찾는다. 정말 올라갔는지 확인이 안 되는 상태는 신뢰를 깎는다.

제출 완료 화면에서 한 번만 보여주는 것으로 해결한다. 이 화면을 벗어나면 다시 볼 수 없고, 그 사실을 한 줄로 알린다. 불편을 감추지 않고 이유와 함께 드러내는 편이, 편의를 위해 목록에 표시를 남겨 익명성을 깎는 것보다 낫다. 이 한 줄이 앱의 성격을 가장 짧게 설명하는 문장이 된다.

## 5. 화면 3개

| # | 화면 | 담는 것 |
|---|---|---|
| **A** | 리뷰 목록 | 상품 정보 + 리뷰들. 빈 상태 포함. 지갑 없이 열림 |
| **B** | 리뷰 작성 | 본문 입력. 자격 상태를 이 화면이 표현한다 |
| **C** | 제출 진행 · 완료 | 증명 생성 3단계. 실패 시 원인 표시. 완료 시 내 리뷰 1회 확인 |

C는 별도 페이지가 아니라 B 위에 덮이는 상태여도 된다. 본문을 잃지 않는 것이 조건이다.

### 설계해야 하는 상태

성공 화면이 아니라 이쪽이 어렵다.

| 상태 | 화면 | 문구 방향 |
|---|---|---|
| 리뷰 0건 | A | 담백하게. 권유 남발 금지 |
| 지갑 미연결 | B | 왜 필요한지 한 줄. 설교 금지 |
| 자격 없음 | B | 사실 + 다음 행동. 사과문 아님 |
| 이미 작성함 | B | 언제 썼는지는 모른다. 아는 척하지 않는다 |
| 증명 생성 중 | C | 3단계 + 경과 시간 |
| 제출 실패 | C | 원인별 문구. 본문 보존 명시 |
| 제출 완료 | C | 내 리뷰 1회 표시 + 다시 못 본다는 안내 |

## 6. 카피 원칙

제품이 자기를 해설하지 않게 한다.

| 쓰지 않는다 | 쓴다 |
|---|---|
| "🔒 영지식 증명으로 신원이 안전하게 보호됩니다!" | (아무 말도 하지 않는다) |
| "Error: nullifier collision detected" | "이 상품에는 이미 리뷰를 남기셨습니다" |
| "자격이 없습니다 😢 죄송합니다" | "리뷰는 구매 확인된 분만 쓸 수 있습니다" |
| "증명 생성 중... 잠시만 기다려주세요!" | "증명 생성 중 · 12초" |

익명성은 자랑하는 게 아니라 작동하는 것이다. 화면에 "익명"이라고 써 붙이면 오히려 의심스러워진다.

## 7. 데모 촬영

### 7.1 시나리오 (3분)

| 시간 | 장면 | 보이려는 것 |
|---|---|---|
| 0:00–0:20 | `/compare`의 블라인드 리뷰 게시판 진입 | 두 방식 모두 같은 상품·같은 입력을 받는다 |
| 0:20–1:00 | `구매 기록 없음`으로 같은 리뷰 제출 | unsafe 게시판에는 글이 생기고 Merkle 게시판은 구매 확인 오류로 막힌다 |
| 1:00–1:40 | `구매 확인됨`으로 전환해 같은 리뷰 제출 | 두 게시판에 글은 생기지만 작성자 신원은 표시되지 않는다 |
| 1:40–2:20 | 같은 구매자로 리뷰를 한 번 더 제출 | unsafe는 다시 게시하고 Merkle는 중복을 막는다 |
| 2:20–3:00 | 두 게시판 결과를 한 화면에 유지 | 원리 설명 화면이 아니라 사용 결과 자체로 차이를 보여준다 |

비교 데모는 생성된 Compact 계약 시뮬레이터를 브라우저에서 실행한다. 실제 Lace·인덱서·proof server 거래처럼 말하지 않는다.

### 7.2 UI 차단과 컨트랙트 거부는 다르다

`/compare`는 버튼만 비활성화하는 화면이 아니라 두 생성 계약 시뮬레이터를 실제 호출한다. 다만 실제 네트워크 거래는 아니므로, 연결된 DApp 거래 검증과 섞어 말하지 않는다. 컨트랙트 거부는 Vitest에서도 같은 입력으로 별도 검증한다.

### 7.3 촬영 전 준비

비교 영상은 `/compare` 한 화면에서 계정을 전환한다. 촬영 전에 아래 순서를 한 번 그대로 재현한다.

- `처음부터`로 양쪽 게시판을 비운다
- `구매 기록 없음` → 같은 리뷰 제출
- `구매 확인됨` → 본문 변경 → 같은 리뷰 제출
- 같은 계정으로 본문 변경 → 다시 제출
- 무편집 원본 보관. 편집본만 남기지 않는다

현재 비교 구간 무음 원본은 `docs/blind-review-comparison-demo.webm`이다. 1280×720, 11.76초이며 실제 Lace 거래가 아닌 생성 계약 시뮬레이터 영상이다.

## 8. 예상 질문

**"nullifier가 결국 사용자 식별자 아닌가."**
같은 사람이 상품 A와 B에 쓴 nullifier는 `H(도메인, itemA, sk)`와 `H(도메인, itemB, sk)`다. `sk`를 모르면 둘을 연결할 수 없다. `reviewerKey`와도 도메인 문자열이 달라 연결되지 않는다.

**"운영자가 명단을 쥐고 있으면 결국 중앙화 아닌가."**
운영자가 정하는 것은 "누가 쓸 수 있는가"까지다. 누가 무엇을 썼는지는 운영자도 모른다. 표적 삭제나 보복이 불가능한 이유가 이것이다.

**"명단이 공개면 프라이버시가 없는 것 아닌가."**
공개되는 것은 파생키 목록이고, 지갑 주소나 신원이 아니다. 명단에 있다는 사실과 특정 리뷰를 썼다는 사실은 연결되지 않는다.

**"직접 컴파일해서 확인한 것인가."**
최종/비교 계약의 Compact 0.31.1 전체 컴파일, TypeScript 빌드, 로컬 시뮬레이터 8건과 `/compare` 브라우저 동작까지 확인했다.
실제 Lace·인덱서·proof server 거래는 아직 확인하지 않았으며 슬라이드에 구분해 명시한다.
